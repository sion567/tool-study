# 分布式·CQRS 读写分离

## 一句话

命令（写）与查询（读）走两条路：**写侧保一致，读侧保速度**，事件负责同步。

## 不变量

- 命令 = 有业务意图的写 → 落**规范化写模型**（事务/约束/不变量全在这侧）
- 落库后发事件 → **投影**到反规范化宽表（按查询的形状存）
- 查询全走读模型：0 join、可缓存、可任意复制多副本

## 画面读法

- 创建订单 → 写库 +1 → OrderCreated 事件 → 宽表 +1 行
- "我的订单" 查询 → 宽表直出答案
- 中间隔着一拍：下单后立刻查，读侧可能还没有（**最终一致**）

## 代价与收益

| | 收益 | 代价 |
|---|---|---|
| 读侧 | 任意伸缩 + 缓存 + 搜索引擎 | 数据双份 + 同步延迟 |
| 写侧 | 不被读流量拖累 | 多一套投影逻辑 |

99:1 读写比的业务（订单列表、商品详情）收益巨大；强一致读（账户余额扣减后立刻验）不能走读模型。

## 延伸

- Event Sourcing：把写模型本身也变成事件流——与 CQRS 常成对出现
- 实现载体：MQ（Kafka）做事件流，ES/宽表做读模型

## 怎么练

- 白纸画双库：一个下单命令 + 一次查询，标出两边数据何时一致
- 思考：哪些查询不能容忍最终一致？（下一秒就要用的数据——直读写库）
