# SOLID·S 单一职责（SRP）

## 一句话

一个类只对**一个变化原因**负责——拆类的标准是"变化的方向"，不是代码行数。

## 反例痛点

`Employee` 一类包揽算薪 + 报表 + 存储：

- 改报表格式 → 重新编译、重新测试**薪资**逻辑（无辜连坐）
- 三个变化方向 = 三个改动理由挤一个文件，影响半径 = 整个类

## 正例

按"谁会变"拆：`SalaryCalc` / `ReportGen` / `EmployeeRepo`。
类数从 1 变 3，但每个类的测试范围缩到 1/3——**收益不在类少，在影响半径小**。

## 判据

问一句："这个类有几个会变的原因？"
- 1 个 → 好
- 2 个以上 → 按变化方向切开

注意：不是越碎越好——从不变化的逻辑没必要拆。

## 怎么练

- 找项目里最长的类，列出它的方法，按"会一起变吗"分组
- 思考：User 类里有 `getAge()` 和 `save()`，该拆吗？（看 save 用的存储会不会变）
